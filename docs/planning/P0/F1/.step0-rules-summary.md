### 1.3 文档编写顺序

docs.md 定义：设计规范 → 视觉原型 → 测试用例表

但 dd-writing-specs 流程要求：需求文档 → 设计文档 → 视觉原型 → 测试用例表

**决策**：遵循 dd-writing-specs 完整流程，先写需求文档，再写设计文档（替代 docs.md 中的「设计规范」概念，设计文档即为架构契约），然后视觉原型，最后测试用例表。

### 1.4 文档命名规则

docs.md 定义：
- 设计规范：`F{m}_{功能名}_设计规范.md`
- 视觉原型：`F{m}_{功能名}_视觉原型.html`
- 测试用例表：`F{m}_{功能名}_测试用例表.md`

dd-writing-specs 默认命名：
- 需求文档：`F{m}_{功能名}_需求文档.md`
- 设计文档：`F{m}_{功能名}_设计文档.md`

**决策**：F1.13 采用完整 4 篇命名：
- `F1.13_来源过滤_需求文档.md`
- `F1.13_来源过滤_设计文档.md`
- `F1.13_来源过滤_视觉原型.html`
- `F1.13_来源过滤_测试用例表.md`

## 3. 既有规格文档的可复用写作模式

参考最近规格文档（F1.11 菜单栏弹窗双击粘贴）：

### 3.1 需求文档写作模式

- 12 章节完整结构，目录含锚点链接
- 文档头部：版本号 + 功能编号 + 优先级 + 存放路径 + 关联文档路径
- FR 编号从 FR-001 起，每条 FR 含「需求」「行为」子章节
- AC 编号格式：AC-F{m}-{n}，Given/When/Then 格式，每条 AC 标注验证方式
- NFR 按性能/稳定性/安全性/兼容性/可访问性/合规性/可维护性分类
- 术语表为 Markdown 表格
- Decision Freedom 分「允许」「禁止」双向

### 3.2 设计文档写作模式

- 10 章节完整结构
- mermaid 图节点全部使用中文业务术语（无英文类名）
- 模块划分表含「新增」「修改」「复用」分类
- 每个模块写「负责/不负责」边界
- 数据流用 mermaid 序列图
- 状态变化用 mermaid stateDiagram-v2
- 关键设计决策含「决策/理由/代价/为何可接受」四段式
- FR 到模块映射表全覆盖

### 3.3 版本记录格式

表格：版本 | 日期 | 变更说明

## 4. CODING_STANDARDS.md 关键规则摘要

- Swift 5.7+ / macOS 13.0+
- Allman 大括号风格，4 空格缩进
- 禁止 `print()`，使用 LogCategory
- UI 状态必须在主线程/@MainActor
- 禁止魔术数字/字符串
- 依赖方向：UI → 业务模块 → Models/Utils
- 测试验证行为，不验证实现
